Use para from Claude Code.

1. Add one MCP server per vault. Run these commands, and add `--scope user` after
   `add` to use a vault in every project:

{{config}}

2. Install the skill, so agents load the rules when they need them:
   $ para skill install
   Reinstall after upgrading para.

3. Restart the session, then check with /mcp.

4. Start with a prompt, as a slash command:
   /mcp__para-<vault>__orient      what para is, and how to work a vault
   /mcp__para-<vault>__bootstrap   an interview that fills a new vault
   /mcp__para-<vault>__review_cycle   how to file a proposal and act on the review
   /mcp__para-<vault>__process_meeting   turn a transcript into one proposal

5. Events record the actor `claude`. Change `--actor` to tell agents apart.

6. Agents normally file a proposal, show the link, and end the turn. Nothing has
   to wait. The rest of this step is only for unattended work.
   `para mcp` watches the vault for the session, with no polling. It sends a
   short message (notifications/message, logger "para") when a proposal you filed
   is decided, a request can be claimed by this install, or a request you
   claimed is cancelled. It holds ids and states only, never vault text, and
   names the tool to call next. The tools `proposal_wait` and `request_wait`
   block up to 60 seconds and return as soon as the state changes.
   Whether Claude Code shows notifications/message is not verified.
   Only a harness that cannot receive notifications needs a background job:
   $ para request wait --timeout 1h
   $ para proposal wait proposal-example --timeout 1h
   Each blocks with no token cost, then call `request_next` or `proposal_show`.

7. Optional: server push into a session. Claude Code channels are a research
   preview. Add "--channel" to the server args. A custom channel such as para is
   not on the approved list, so start the session with:
   claude --dangerously-load-development-channels server:para-<vault>
   Team and Enterprise organizations must enable channels first. Para works
   without it: use step 6 or call the wait tools.

8. Optional: let para start the agent when a request can be claimed on this machine.
   THIS SPENDS TOKENS: every run starts a Claude Code session, billed to whatever
   account claude uses. Para starts nothing unless the file below exists on this
   machine. It is never in the vault and never synced. Write it with mode 600:

   $PARA_HOME/vaults/<vault>/agent.json
   {
     "command": ["claude", "-p", "Use the para tools: call request_next to claim a request, work only on that request, report with request_note, and finish with request_done or request_fail."],
     "max_concurrent": 1,
     "daily_limit": 10,
     "cwd": "/home/you/work"
   }

   command is an argument list, not a shell string. daily_limit counts starts per
   local day and survives a restart; max_concurrent is how many run at once. The
   environment of the command has PARA_REQUEST (the request id that woke it),
   PARA_HOME, and PARA_VAULT; nothing else from the vault is passed. Only the
   machine that is the vault's request runner starts anything.
   This example, claude -p with those words, is untested: it was written from
   the documented flags and was not run against a real session. Try the command
   by hand first, with PARA_REQUEST set, and check that the para tools are
   allowed for non-interactive runs.
   $ para agent status
   $ para doctor

Para cannot stop an agent from using other tools. To enforce "no external action
without approval", use Claude Code permission rules or a hook. A hook can run
para proposal approved with the sha256 of the target, one NUL byte, and the draft;
it exits non-zero unless the owner approved that exact text.
