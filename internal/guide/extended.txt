Use cases. Every line starting with "$" is a real command. Ids are examples: use the
id that the creating command prints.

1. Start a vault
  $ para init life ~/vaults/life
  $ para area add "Home"
  $ para project add "Paint the hall" --area area-home
  $ para task add "Water the plants" --area area-home --due 2026-11-08 --recur weekly

2. Capture and triage
  $ para inbox add "call the plumber about the leak"
  $ para inbox list
  $ para inbox triage inbox-example --to task --area area-home
  $ para inbox triage inbox-example --to note --area area-home
  $ para inbox triage inbox-example --to drop

3. A project with a task DAG
  $ para project add "Move the server" --area area-home
  $ para task add "Order the disk" -p project-move
  $ para task add "Mount the disk" -p project-move --depends-on task-order
  $ para task depends add task-mount task-order
  $ para task due task-mount 2026-12-01
  $ para graph project-move
  $ para next
  $ para task block task-mount --reason "Asha said wait for the delivery, this project only"
  $ para task done task-order

4. Ask someone: self-serve first, then the request, then the reply
  $ para search "launch freeze"
  $ para route billing
  $ para rfx add "Can the portal launch before the audit?" --route domain-billing --self-serve "read policy-logging, searched the wiki" --to person-ada-example --via email
  $ para rfx draft rfx-example --text "Hi Ada, can the portal launch before the audit?"
  $ para rfx target state rfx-example person-ada-example sent
  $ para rfx reply rfx-example --from person-ada-example --outcome no --why "Audit freeze" --url https://chat.acme.example/t/1 --text "Not before January."
  $ para constraint list
A "no" with its reason becomes a constraint, so nobody asks the same question twice.

5. An area for a system you run
  $ para area add "Home lab"
  $ para area link add area-home-lab "Runbook" --kind runbook --target ~/doc/lab/runbook.md
  $ para task add "Renew the TLS certificate" --area area-home-lab --due 2026-12-01 --recur "every 365 days"
  $ para note add "Switch ports" --area area-home-lab --tag network --body "Port 3 is the uplink."
  $ para where lab
  $ para area show area-home-lab
area show lists the area's incidents and recurring tasks; where lists its open incidents.

6. Hand a task to someone, and see what you wait on
  $ para task assign task-example person-ada-example
  $ para task add "Summarize the alerts" --area area-home-lab --assignee agent:scribe --recur daily
  $ para task list --assignee person-ada-example
  $ para waiting
  $ para who ada
A task assigned to another person or to agent:<name> leaves para next. It shows in para waiting, with the requests you sent, and under the person in para who. A recurring task assigned to an agent queues a request.

7. Recurring work: done makes the next one
  $ para task add "Rotate the backup disks" --area area-home-lab --due 2026-11-15 --recur monthly
  $ para task add "Check the UPS battery" --area area-home-lab --recur "every 90 days"
  $ para task done task-example
  $ para task done task-example --skip
recur is daily, weekly, monthly, or every <n> days. Done creates the next task, due one step later (a late task moves to the next date that is not in the past) and linked back with previous. --skip advances without doing this one. Para has no scheduler: nothing recurs until you mark the task done. Any other recur value is a lint warning.

8. An incident: the record, the timeline, the follow-ups
  $ para incident add "Atlas down" --severity sev1 --area area-home-lab
  $ para incident note incident-example "Rolled back the 08:40 deploy"
  $ para incident status incident-example mitigated
  $ para task add "Add a canary stage" --incident incident-example
  $ para incident status incident-example resolved --note "canary task filed"
  $ para incident list --all
  $ para search canary
  $ para today
Para is not a pager: alerts stay in monitoring (your pager, Alertmanager, a status page). Para holds the record and the follow-up tasks. Open incidents come first on para today. Resolving an incident with no follow-up task prints a warning. Resolved incidents stay searchable.

9. Before you contact someone
  $ para who ada
  $ para interaction list
  $ para org person show person-ada-example

10. Policies and exceptions
  $ para ingest --url https://wiki.acme.example/policies/logging --title "Logging policy" < logging.txt
  $ para policy show policy-logging
  $ para rule list
  $ para exception add --policy policy-logging --kind bug --by "Jordan Example" --rule R4
  $ para exception expiring

11. Agents: MCP tools and the request queue
  $ para mcp config --client claude
  $ para request add "Summarize the portal project" --link project-portal
  $ para request accept request-example
  $ para request list
  $ para tui

12. Export: carry a document to another window
  $ para export policy-logging --as slack --to clipboard
  $ para copy policy-logging --as email

13. Browser and phone: the server, keys, and the service
  $ para key create phone --scope vault:read --scope vault:write --ttl 30d --print-url --url http://127.0.0.1:7700
  $ para key list
  $ para serve --check
  $ para serve
  $ para service install
  $ para service start
  $ para service status
  $ para service login-admin
  $ para key revoke phone
The server listens on 127.0.0.1:7700 by default and every request needs a token.

Where does this go?
  You have                                   It goes in
  a deadline you owe                         a task with --due
  an ongoing responsibility (no end)         an area
  a bounded outcome                          a project (in an area)
  something you wait on a person for         an rfx, with a reason if refused
  a task a person or an agent owes you       a task with --assignee; para waiting lists it
  a chore that repeats                       a task with --recur
  a fault in a system you run                an incident, with follow-up tasks (alerts stay in monitoring)
  a refusal with its reason                  a constraint (rfx reply --outcome no)
  who someone is, how to reach them          org person, contacts, interactions
  reference facts you will look up           a note
  a plan, doc, runbook, or repository        stays where it lives; link it from the area or project
  a phone or browser view of the vault       para serve, with a key from para key create
  a meeting, a reminder at a time, a page    not para: use a calendar or a pager
