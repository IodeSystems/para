7. Recurring work: done makes the next one
  $ para task add "Rotate the backup disks" --area area-home-lab --due 2026-11-15 --recur monthly
  $ para task add "Check the UPS battery" --area area-home-lab --recur "every 90 days"
  $ para task done task-example
  $ para task done task-example --skip
recur is daily, weekly, monthly, or every <n> days. Done creates the next task, due one step later (a late task moves to the next date that is not in the past) and linked back with previous. --skip advances without doing this one. Nothing recurs until you mark the task done, except through para tick (use case 17). Any other recur value is a lint warning.

11. Agents: MCP tools and agent work
  $ para mcp config --client claude
  $ para --actor claude --why "Owner asked for it" doc edit note-example --title "Better title"
  $ para vault config list
An agent with only a shell passes --actor and --why: its writes then follow the MCP rules. Vault settings: para vault config list, get, set, unset; an agent may change only align.days and goals.active_limit.
  $ para request add "Summarize the portal project" --title "Summarize the portal goal" --link project-portal
  $ para request accept request-example
  $ para request list
  $ para investigate task-example --hint "check the wiki"
  $ para task delegate task-example --agent scribe --hint "start with the runbook"
  $ para task resolve task-example --outcome partial --note "Data moved, DNS not." --follow-up "Move DNS"

Ask agent (op investigate): sends a task, meeting, question, ask, goal, or agent work to an agent as queued agent work, linked to the item. The text is optional. For anything but a question the agent does three things, with its own tools (read-only outside para): fills in missing details (done_when, do_url, do_command, or steps, effort, context with sources); checks whether it is already done in the owner's sources, and closes it with evidence the owner can open when an observed act shows it done, without asking the owner to confirm; and rechecks its assumptions (depends_on, due date, who does it, whether it is still needed). It ends with a short note when nothing changed. With no text the work is "Investigate: <title>" ("Find evidence: <title>" for a question, which the agent answers with sources). With text the work is "Ask: <title>": on top of the three things, the agent answers the text in words, or fixes the item: rewrite (doc_edit), retype (doc_retype, task_to_question), split (task_add with parent), drop or duplicate (close with that outcome), or add context. Every change leaves a receipt, and every claim cites a source: a guess is not a source. One run is open per item: ask again adds the text to it. The item shows "Agent looking" while the work is queued or claimed. When the agent ends the work, the item shows "Agent replied" with the resolution note, from the work itself; the owner answers back with respond on that agent work. Only a person can do this (para investigate); an agent cannot. Para fetches nothing itself, and starts an agent only when dispatch is set up. para question investigate <id> --how <text> is the same call for a question.

Resolve and delegate: task resolve closes a task with an outcome: done (the default; finished; same as task done, recurrence included), partial (some of it done), dropped (nobody needs it any more, and nobody said no), duplicate (another item is the same work), superseded (another item replaced this way of doing it), declined (someone said no), failed (tried and could not be done), or rerouted (another task, Ask, or outside system holds it now). partial needs a --follow-up or a --note that says why there is none. dropped needs a --note. duplicate and superseded need --link, the id of the replacing item. declined needs --reason, --declined-by owner or other (--declined-person optional), and --source (a document id or URL) or --date. failed needs --tried and --stopped-because; --retry-after puts it back in health and the agenda on that day; para task list --outcome failed finds them. rerouted needs --to (a vault id or a URL) and --reason; dependents move to a vault task or Ask, otherwise they are released with a warning. declined and dropped close the open Asks that hang on the task only, with the reason; failed and rerouted list them as needing a decision. Each --follow-up is a title; it makes a task in the same goal or area, and the open tasks that waited on the closed one move to the first follow-up (or to the link, when there is none), so nothing waits on work that did not finish. dropped releases its dependents. --done-when changes the done condition first and keeps the old text under ## Outcome. The outcome is stored in the task's frontmatter and the note under ## Outcome; lists and history show it. task delegate gives a task to an agent: it assigns agent:<name> and queues agent work "Work on: <title>" linked to the task, with the hint, the done_when, and the standing instruction to use its own tools, take no external action without the owner's go-ahead in chat, and report with a resolution and sources. The agent defaults to request.runner; with none set the work is queued and the output says how to set one. A second delegate adds its hint to the open work. The row shows "Agent working" until the agent finishes; the task closes only if the agent's own close is allowed.

13. Browser and phone: the server, keys, and the service
  $ para setup
  $ para login
  $ para login
  $ para serve sessions
  $ para serve logout
  $ para serve status
  $ para key create phone --scope vault:read --scope vault:write --ttl 30d --print-url --url http://192.168.1.76:7700
  $ para key list
  $ para serve --check
  $ para serve
  $ para service install
  $ para service start
  $ para service status
  $ para key revoke phone
para setup walks a new machine through doctor, domains (each vault has one; the machine records the list it holds in machine.domains, and a vault opens only on a machine that lists its domain), the first vault, the service, sign-in, and an optional agent hookup; a rerun skips what is done, and each prompt has a flag; --dry-run prints every step and write and changes nothing. Sign-in is skipped while every served vault has an unexpired login key (--login forces it). para login signs the browser in; with no server running it says so.
The server listens on 127.0.0.1:7700 by default and every request needs a token.
"para login" signs this browser in to every vault the server serves, one tab per vault
(--vault for one). Each tab gets a new login key, vault:read, vault:write, rfx:draft and review:decide, that lasts 30
days (--days, at most 90); the web app renews it when it is within 7 days of its end. It finds
the running server itself (var/serve.json in the para home), so it needs no URL. "para open"
signs the browser in the same way when no login key of the vault is active; an agent cannot sign the browser in. "para serve sessions" lists the
login keys and "para serve logout" revokes them. --admin signs in with the admin token, which
works from this machine only. For a phone or another machine, make a key with --print-url and
give the URL of that machine.
The web app can show browser notifications while a tab or the installed app is open: Help, then Notifications. It is off by default, set per vault in that browser, and a notice names a kind and a count only (answer to check, agent work that needs you, incident). There is no push service.

11. Agent writes: receipts, undo, and outward actions
  $ para receipt list
  $ para receipt show receipt-example
  $ para receipt check receipt-example verified
  $ para receipt undo receipt-example
  $ para agent activity --since 2026-11-01
Agents change the vault with ops. Each write leaves a receipt: who, which op, why, sources, how to verify, and the document before and after. You read receipts in the web app under Recent agent writes, newest first, each with its undo command to copy, and on the Receipts page: filter by agent, op, check, and day; Undo (it asks for a confirm in the row), Mark verified, or Mark wrong with a note. Its Outcomes section, and para report outcomes, count task closes by outcome and by agent, the review items you declined with your reasons, and the writes undone. receipt undo puts the document back if nothing changed it since, and refuses with the reason if something did. A vault write that `receipt_undo` can reverse applies at once, with a receipt you can undo; bulk or risky changes need no approval step. Para sends nothing.

12. Old dossiers and outward drafts
  $ para proposal list
  $ para proposal show proposal-example
  $ para open proposal-example
  $ para io list
  $ para io approve io-example
Older vaults hold dossiers (proposals) that were closed when the vault moved to format 8. You read them, read-only, with para proposal list and para proposal show; para open shows one in the browser. Nothing new is filed as a dossier.
Before an agent sends an outward act (an email, a post, a ticket, a PR, a deploy, a remote document edit), it drafts it as an outgoing io item (io_add direction out). You read the exact text with para io list, and approve it in the web app or with para io approve <id>. An agent may approve only when it passes your verbatim words in the chat (owner_said). Right before it sends, the agent reads the channel again and runs the pre-send check (para io send-check <id>, or the tool io_send_check): a new message in the conversation since you approved holds the draft and brings it back to you. The agent sends the text with its own tool and reports it (para io send, or the tool io_send); until then the draft is not sent. When you send by hand, run para io send-check <id> first. A message that waits for your reply is a reply obligation (Reply to <sender>), due io.reply_days after it came; your threaded reply closes it. para io stats gives the numbers per source. A change only you can decide arrives as a question (para questions).

14. Questions: unknowns, decisions, and inputs are not tasks
  $ para question add "Which config path does prod use?" --project project-move --kind decision --option /etc/atlas --option /opt/atlas --recommended /etc/atlas
  $ para question add "Who signs off on the window?" --root
  $ para task add "Deploy to prod" -p project-move --depends-on question-example
  $ para questions
  $ para answer question-example --choice 1 --why "Matches the container image"
  $ para question ask question-example --to person-ada-example --via slack --route domain-billing
  $ para question show question-example
  $ para question drop question-example --reason "Out of scope now"
  $ para task to-question task-example --kind decision --option "Nov 14" --option "Nov 21"
  $ para task done task-example --note "Rolled out; old keys revoked"
  $ para question depends add question-example task-example
  $ para question edit question-example --title "Which config path does prod use?" --option /etc/atlas --option /opt/atlas
A question can wait on a task, an ask, or another question (question depends add; a cycle is refused). depends set <id> <on> records what any task, obligation, ask, or question waits on; --optional marks it better before: it is shown under Waits on with an optional chip and never holds the item (no wait, no start date, no due date passed down, no cycle); run it again without --optional to make it required, or --remove to take it away. depends set <id> --reason <text> blocks a task with a reason in words. context <id> lists waits on and blocks. An agent may answer with sources, which can be your own words in the chat; the answer is final and leaves a receipt, and receipt undo reopens it. An answer an agent proposed in an older version shows as a proposed answer until you answer the question. A question has exactly one scope: --project, --task, --area, or --root for the whole vault. An open question blocks the tasks that depend on it in graph, next, and task start; an answer frees them. A decision needs its reason. para questions lists what is open, the ones that block the most first. An answer is stored in the question under "## Answer", with who and when; never put a secret in it, say where it is kept. para rfx reply with outcome answered or no answers a question that was asked with question ask, when a person replies. When an agent records the reply or the answer, it is only a proposed answer with its sources: it waits under "Answers to check" until you accept it (para question accept, which lets you change the text first) or reject it with a reason (para question reject). task to-question moves the tasks that waited on a task to the new question and drops the old task.

15. Meetings: ask, book, hold
  $ para rfx add "Can the portal launch before the audit?" --route domain-billing --self-serve "read policy-logging" --to person-ada-example --via email
  $ para meeting add "Launch window sync" --with person-ada-example --rfx rfx-example --scope project-portal
  $ para meeting schedule meeting-example --start 2026-11-04T10:00:00-05:00 --end 2026-11-04T10:30:00-05:00
  $ para meeting list
  $ para meeting show meeting-example
  $ para meeting hold meeting-example --notes "Agreed to ship in January." --answer question-example="December" --action "Send the plan | person-ada-example | 2026-11-10" --project project-portal
  $ para meeting cancel meeting-example --reason "Ada is out"
Asking for a meeting is progress: the linked ask gets a meeting target, requested and then scheduled, and stays on para waiting until the meeting is booked. The body lists the questions to settle: the linked asks and the open questions in scope. Times are RFC 3339 with the zone they were booked in, and show in your zone. hold records your notes, sends replies through para rfx reply (a no still becomes a constraint), answers through question answer, and makes each action item a task with its assignee and a link to the meeting. An ask made in the meeting and not answered in it stays a wait. A meeting is an obligation of kind meeting (a commitment, something you owe someone, is the other kind), with scheduled and end instead of due, in obligations/; para meeting commands are aliases of para obligation add, schedule, and attend, and para close holds (no outcome), cancels (dropped), or skips it. Moving a booked meeting keeps the old time in its notes. Tasks have other kinds, a call and work with someone: para task add "Call Ada" --kind call --with person-ada-example --scheduled 2026-11-05. para task attempt call-example --result no_answer --retry 2026-11-06 logs an attempt in the Attempts section and moves the call; after three attempts it shows as stuck. Work with someone closes with para task resolve and an outcome; a commitment with para close. Para does not record or transcribe a meeting. For a transcript, an agent uses the prompt ingest_source and updates the vault with ops, each with a receipt.

16. Agenda and calendar
  $ para agenda
  $ para agenda --days 14
  $ para agenda --zone Europe/Berlin
  $ para calendar export --days 30 --to file:/tmp/para.ics
  $ para calendar export --to clipboard
Without a date flag, para agenda is the home view: what needs you in value order across all vaults. Value order puts what you can do now first (incidents, then anything overdue or due within order.due_soon_days, default 2, by date, then the reply batch: asks made to you and messages that wait for your reply that take under an hour, longest waiting first, then focus: order.focus_count items, default 3, best by impact per effort, doubled when its date or its goal's date is within order.goal_soon_days, default 14, then recheck: items overdue by more than order.stale_days, default 30, oldest first, to ask if they are still needed, then the rest by the same score; set effort with --effort xs, s, m, or l) and what cannot start yet last (a meeting after today, a call scheduled later, and work that waits on one), by the day it can start. With --by-date, --days, or --zone it lists meetings, tasks due, asks to follow up, and exceptions due for review, earliest first, in local time. A date is a calendar day in your zone, so a meeting at 01:00 UTC is the evening before in New York. Anything dated before today is overdue. In the web app, Agenda is the home screen; its By date toggle shows this dated view, and it is the only screen that switches vault. calendar export writes an .ics of scheduled meetings and due tasks; it goes through the egress check and logs an event, like export. A calendar app reads the file. Para never writes an external calendar.

17. Scheduled work: tick
  $ para tick
  $ para tick --all
  $ para serve
One idempotent pass per vault: it makes the next occurrence of a recurring task that was marked done by hand, makes the agent work item for a due recurring task assigned to agent:<name> that has none, names the asks to follow up that are due, and reconciles. It is safe to run twice. A synced vault lives on two machines, so tick runs only on the install named in the vault's .para/vault.properties: request.runner=<install id> (para tick prints the line to add). Run it from cron, or let para serve run it every minute (tick.interval in $PARA_HOME/server.properties; off turns the timer off). Tick acts as actor tick. An agent work item it makes is queued only when request.surfaces in vault.properties lists tick (for example request.surfaces=cli,pwa,tick); otherwise it is proposed and waits for para request accept.

18. Dispatch: start an agent when agent work is ready (off by default, spends tokens)
  $ para agent status
  $ para doctor
  $ para request add "Summarize the portal project" --link project-portal
Dispatch is off unless this machine has $PARA_HOME/vaults/<vault>/agent.json. It is never in the vault. With it, para serve starts the command when agent work can be claimed on this install, with the id in the environment variable PARA_REQUEST. The command claims the work itself, so a prompt that tells the agent to call request_next is enough. Every run starts an agent, so dispatch spends tokens; max_concurrent (default 1) and daily_limit (default 10) bound it, and the count survives a restart. The command is an argument list, never a shell string; the only vault-derived value it receives is the request id, which must be a plain id. A run's output goes to a log file in the state directory, mode 0600. para mcp --help-claude and para mcp --help-dun show the file.

19. Journals by level: day, week, month
  $ para journal
  $ para journal show 2026-w44
  $ para journal summary 2026-11-01
  $ para journal daily 2026-11-01
Para keeps a journal of the day, the week, and the month, built from events: counts and links. para tick makes them: the previous local day once it has ended, the previous ISO week after Sunday, the previous month after its last day. It catches up on missed periods after downtime, up to 14 days back, and never rewrites one that exists. This part is mechanical and spends no tokens. Run para tick from cron, for example "5 * * * * para tick --all" (hourly is enough; it is idempotent), or let para serve run it. It still needs request.runner in .para/vault.properties.
For prose, set journal.agent=<name> in .para/vault.properties. On a vault at format 7 or later, the next tick makes one obligation, "Daily journal summary", owed by that agent (a recurring artifact, use case 28), once per vault. Each day its occurrence asks the agent to write the summaries of the journals that ended: the day, and a week or month when one ended, a week from the day summaries, a month from the week summaries. THE NARRATIVE SPENDS TOKENS: one agent run per day that had events. A day with no events gets no request, and its occurrence closes skipped. Unset journal.agent to pause it; close it dropped to stop it. Below format 7, tick queues one request per journal instead. The agent uses the prompt loop, part Produce, and the op journal_summary, which writes one marked section of the journal, recorded under its actor. Your own text in the journal is never touched. Without journal.agent you get the mechanical journals only.

Merge, archive, notes, and waiting
  $ para doc merge task-weekly-sync task-weekly-sync-moved
  $ para doc merges task-weekly-sync
  $ para doc archive task-old-standup --reason "It moved to Tuesday"
  $ para notes read task-weekly-sync
  $ para notes edit task-weekly-sync --hash sha256:example --md "Room 4 is booked."
  $ para task to-asks task-waiting --person person-example
  $ para task block task-cert --reason "Ops said the CA is down until Thursday" --until 2026-11-12
  $ para meeting schedule task-weekly-sync --start 2026-11-10T10:00:00Z --end 2026-11-10T11:00:00Z --calendar-event room@acme.example=room
doc merge folds a duplicate of any type into the item that stays: every link to the duplicate points to the one that stays, its people, Asks, dependencies, calendar events, and notes move over, and the duplicate leaves every list and search. Its id still opens, and the page of the one that stays lists it under merged from. task resolve --outcome duplicate does the same for a task. doc archive is para's delete: the item leaves every list and its links still open. A meeting that moved is merged into the new one, or archived. Both leave one receipt, and receipt undo reverses all of it. Notes are the ## Notes section of any item: notes read gives the text and a hash, and notes edit replaces the notes only when the hash is still current, so two writers never lose each other's words; the web app has a notes editor on every item page. Waiting on a person is an Ask, not a task: task add warns on a title like "waiting on Ada", health lists such tasks, and task to-asks makes one Ask per person and closes the task. task block --until <date> sets the follow-up date: the blocked task leaves next and the agenda until then and comes back on the day; task list still shows it, with "returns <date>". The due date is when the work must be done, and never hides it. A meeting can hold several calendar events (the invite, the room, a prep slot); calendar compare matches any of them and calls an event with no attendees over a meeting an alias of it. When you paste or dictate something to an agent, it saves your words as an io item first, so nothing is lost if the rest fails.

  $ para rfx path add rfx-example person-bo-example --medium email --reason wrong_owner --why "Ada does not own the quota" --nudge 2026-12-01
  $ para rfx target state rfx-example person-ada-example no_reply --reason capacity --why "On leave"
An ask keeps a path log: each target is a try, with the medium, when it was added and sent, and how it went. rfx paths lists it, and when the ask is stalled (every target unanswered, the follow-up date passed, or a send a week old) it lists the next moves: other contact methods for the person, ranked by the preferred contact and by what their notes say; someone else with the same domain role, team, or group; an introduction; a meeting or call; self-serve again; a blocker. Each line shows how many times and how lately the person was asked across all asks. rfx path add takes a move as a new target on the same ask, with a reason code (wrong_owner, no_owner, policy_conflict, policy_unclear, no_response, capacity, needs_approval, tool_gap, other), a reason in words, optionally the policy, exception, or domain it is about (--about), and a new follow-up date; it records the attempt in the ask. Para sends nothing: you send it. A person's structured away_until and quiet_days (set with doc edit) hold a repeat back; only a person can pass --override. Notes in the body are not read for this. An agent can add the next move with rfx_path_add. The web app shows Next moves on the ask page. target state no_reply records no_response unless you give another reason.

24. Upgrades: the binary, the notes, the vault format
  $ para upgrade
  $ para changes --since 0.1.0
  $ para vault upgrade status
  $ para vault upgrade --dry-run
  $ para vault upgrade
  $ para vault upgrade --undo up-meeting-as-task-20261103120000
  $ para lint --file
From a git checkout (the one the binary was built from, or --src), para upgrade refuses when tracked files have uncommitted changes, runs git pull --ff-only, then make install, which restarts the para service. It never commits or pushes. Without a checkout, or with --release, it installs the newest release from GitHub: the manifest's minisign signature is checked with the key built into para and the download's sha256 with the manifest, an older release is refused (--force installs it), and the service is restarted. It then prints the changes between the old and new versions; for each vault this machine holds it prints the dry run of the pending automated steps and asks before it runs them (--yes runs them, --no-vault-steps skips them), and files the judgement steps as agent work. The notes are embedded in the binary, one file per version with two sections: People and Agents. An agent that sees "para changed since your last session; call changes" in the server instructions calls `changes`. An MCP server keeps running the binary it started with, so after an upgrade it refuses tool calls with both versions named and the steps to reconnect; para doctor warns about an MCP server or a service that runs a replaced binary.
A vault records format_version in .para/vault.properties. Each upgrade step is one of two kinds. An automated step is a deterministic rewrite through the vault: --dry-run lists the documents, a real run is one batch with one event per document, and --undo restores the files on the machine that ran it (the backup is in $PARA_HOME, never the vault). The first step rewrites type: meeting files as tasks of kind meeting and keeps content and links; step 7 makes meetings, commitments, and asks to you obligations in obligations/ (ids, text, and old fields kept), and refuses while a machine seen in 14 days runs an older para (--force runs it anyway). A second machine that sees the new format_version does nothing. A judgement step is a change no program can make, such as a done_when for each open goal and task; --file queues it as agent work titled "Vault upgrade: ...", with instructions and the list of documents, and `vault_upgrade_status` lists what is pending. The agent makes the changes with ops, and the step clears when no document is left to change. Old documents stay readable until then. Pending steps show on the Agenda and in the orient prompt.
vault upgrade, vault upgrade status, lint, health, and doctor end with one verdict line: ✓ when all is well, ! when it passed with warnings or work is still pending, ✗ when it fails. On a terminal error is red, warn yellow, and ok green; NO_COLOR or --json turns colour off. The upgrade verdict names the format before and after, the batch ids, lint errors and warnings, and the judgement steps still pending with the command to queue them. A run that stops at a step, or leaves lint errors, exits non-zero. After a run, and with para lint --file, the lint findings go to one agent work request titled "Vault check: N errors, M warnings" (kind vault-check); an open one is updated, not filed again. The agent fixes the data with ops, or, when para is wrong, changes nothing and ends with a bug report to forward to para's developer. Run /para loop to work it.

A large goal can carry a brief: why, confidence, alternatives (including do nothing), unknowns, signals, a pivot, extensions, ecosystem, a rank, and a validation state (idea, validated, active, pivoted, stopped). Every part is optional. An agent drafts or challenges it with the prompt grill_goal, part Brief, and writes it with doc_edit; you choose among alternatives by answering a decision question. A signal reading is added with a source, the rank is yours, and goals compare side by side with no score. A pivot date that has come, or a reading that is due, shows on the agenda with the reason. `health` warns on a goal with signals and no reading, and on a pivot date that has come.
  $ para goal signal add project-pilot "Pilot runs" --value 3 --source note-pilot-log
  $ para goal rank project-pilot 1
  $ para goal compare

27. What needs you from the inbox: priority, triage rules, the digest
An incoming message needs you only when the sender waits for your reply (expects response), the sender (or a group they are in) or the source is priority high, or a triage rule says so. The rest is listed in the day's journal under Inbox digest and in the Inbox under Digest, until you file or drop it.
  $ para priority set group-family high
  $ para priority set src-newsletters low
  $ para triage run --dry-run
  $ para triage run
Triage rules are .para/triage.yaml, read in order. Each rule matches on from (a person or group id), tag, class, vendor, medium, or subject (contains), and takes actions needs_you, digest, link <id>, tag <tag>, or mute (drops it with reason "muted by rule N"). Tags and links add up; the first rule with needs_you, digest, or mute decides.
  rules:
    - name: release notes
      match: {from: group-vendors, subject: "release notes"}
      actions: [digest, tag release]
    - match: {vendor: teams, tag: lunch}
      actions: [mute]
Each change has a receipt naming the rule; undo it on the Receipts page and the rule leaves that message alone.

28. Recurring artifacts: reports, status messages, journal summaries an agent owes
  $ para note add "Weekly status template" --body "Done, next, blocked (on whom), dates at risk."
  $ para obligation add "Weekly status to the team" --owed-by agent:claude --produce message --template note-example --to group-example --medium email --recur weekly --due 2026-11-13
What recurs and who gets it is yours: a commitment owed by an agent, with what it produces (journal, report, message, doc, or other), a template (a document, or the text), and for a message who it goes to. When an occurrence comes due, tick asks the agent for it (agent work of kind produce, linked to the occurrence) and makes the next occurrence of a series. The agent writes it (a note, a journal summary, or an outgoing draft) and records it on the occurrence. A note or journal summary is in the vault and can be undone, so the occurrence closes done at once; reopen it if it is wrong. A message stays open as ready until you approve it (para io approve); it is never sent before that, and only the newest ready one of a series needs you. Like other tick work, it is made only when request.surfaces lists tick. The obligation page in the web app shows the owner, the template, and the last artifact with its state; New recurring artifact on the Obligations page makes one.

29. Idea pools: good ideas kept until a trigger comes
  $ para idea add build-day "Sensor dashboard" --text "Plot the garden sensors live."
  $ para pool list
  $ para pool pick build-day task-example
  $ para pool pick build-day --skip
A pool is the open tasks, goals, and questions put off someday that carry its tag. You write the pools in .para/pools.yaml: a name, a tag (default the name), pick (default 1), an area for new ideas, and when, one of: date (YYYY-MM-DD, with recur such as quarterly), exists (an open obligation, task, or goal with a tag whose date is within within_days, default 14), or closed (an item id, once it is closed). An agent offers a pool in words; it does not write the file. A title and a sentence are enough for an idea; an agent fills in the rest when the pool fires (fill-gap, within gap.daily_cap). When a pool fires, Next and the agenda show one card for it ("Build day: pick 1 of 4 ideas"), its ideas ranked by the value order's score; the ideas do not flood Next. Pick brings the checked ideas back and makes each task prep of the obligation that fired the pool, so it shows in that obligation's hub; the rest stay put off. Pick or Skip this round ends that instance: the pool asks again at the next date or the next tagged obligation. The Pools page (menu) lists every pool, its trigger, size, and next fire, and has Add idea to pool.
30. Publish: chosen documents as plain files, for readers without para
  $ para publish set area-example design
  $ para publish dir design ~/shared/design
  $ para publish preview design
  $ para publish design
Some documents (design notes, rules, runbooks) are for people or agents that do not run para. A read-only key would show them the whole vault; a publish set shows them only the documents you put in it. publish set lists the sets a document is in (its frontmatter publish); no sets takes it out. Only you set it: an agent's write that changes it is refused, because it decides what leaves the vault. A set's folder is a path on this machine, kept in $PARA_HOME/vaults/<id>/publish.json and never in the vault. para publish <set> writes one markdown file per document (named by its title and a short hash of its id, the same every run) and an index.md, each with a first line that says para generated it. A wikilink to a document in the set becomes a relative link; any other becomes plain text, as export writes it. An embed or block reference of a document outside the set refuses the run, and nothing is written. The run prints the people, groups, and io items the documents link, for you to check before you share. The folder is replaced in full each run, so a document taken out of the set disappears; a folder that holds a file para did not write is refused, and a folder inside the vault too. Each run logs one egress event: the set and the hash of a manifest of ids and content hashes (kept beside publish.json). A run follows egress.default: under deny it runs only when you set egress.publish allow. The banner is publish.<set>.marking, else classification. An agent can preview a set (files, link rewrites, the review list, what refuses it) with publish_preview; only the terminal writes the folder.
31. Sent for you: messages an agent may send without your review, stamped
  $ para io add "Got it, thanks." --direction out --to person-example --medium slack --expects none --voice for_me --agent worker-example --kind acknowledgement
  $ para delegation run io-example
  $ para io list --direction out --voice for_me --all
A message an agent drafts for you goes out as you only after you approve it (as_me, the default; no stamp). Some messages you never need to see: an acknowledgement, a scheduling reply. Those are for_me: the agent sends them for you without your review, and the text ends with a stamp that says an agent sent it and you did not review it. You decide which in .para/delegation.yaml, your file (an agent offers a rule in words; it does not write it): rules, each matching by medium, class and vendor (of the source in via), to (person or group ids, a group matches its members, or address patterns such as *@example.test; every recipient must match), kind (a label the agent puts on the draft), max_chars (of the text without the stamp), and agent (which agents may use it). The stamp is, first found: the rule's stamp, the agent's (agents: {<name>: {stamp}}), the file's stamp, the setting io.stamp, then "— sent by {agent} for {owner}; not reviewed by {owner}". Placeholders: {agent}, {owner} (the setting owner; a person id is read as their name), {date} (the day the draft was made), {rule}. Para appends the stamp when the draft is made and refuses an edit that removes it. An agent sends a for_me draft without your approval only when a rule matches when it sends, the stamp is at the end, and the pre-send check passed in the last 30 minutes; a message that came in after the draft holds it for you. The item and its receipt name the rule (allowed_by). With no rule that matches, the draft waits for you like any other; Approve as you takes the stamp off, and it goes out as yours. In the web app, the draft shows As you or For you, stamped: <rule>, with the stamp; the Outbox has Sent for you, the messages agents sent in your stead.
