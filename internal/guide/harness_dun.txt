Use para from dun.

1. Add one server per vault to `servers` in .dun/dun.local.json for this machine,
   or dun.json for the project:

{{config}}

2. Install the skill, so agents load the rules when they need them:
   $ para skill install
   Reinstall after upgrading para.

3. Check with /mcp.

4. Start with a prompt, as a slash command:
   /para-<vault>:orient      what para is, and how to work a vault
   /para-<vault>:bootstrap   an interview that fills a new vault
   /para-<vault>:review_cycle   file a proposal, open it, and record the owner's decision
   /para-<vault>:process_meeting   turn a transcript into vault updates
   /para-<vault>:journal_lod   write a day, week, or month journal summary

5. Events record the actor `dun`. Change "--actor" to tell agents apart.

6. Agents change the vault with ops and tell the owner in the chat. Before an
   outward action they file a proposal, open it, and ask in the chat. Nothing has
   to wait. The rest of this step is only for unattended work.
   `para mcp` watches the vault for the session, with no polling. It sends a
   short message (notifications/message, logger "para") when a proposal you filed
   is decided at a terminal, a request can be claimed by this install, or a request
   you claimed is cancelled. It holds ids and states only, never vault text, and
   names the tool to call next. The tools `proposal_wait` and `request_wait`
   block up to 60 seconds and return as soon as the state changes.
   dun adds the message to the conversation at the next tool result or turn. It
   does not start a turn on an idle session: this is read from dun's code, not
   run.
   To let a notification start a turn on an idle session, add "wake": true to
   the server in dun's config. It is off by default, because each wake is a paid
   turn; dun allows one wake per 30 seconds and 20 an hour per server.
   Only a harness that cannot receive notifications needs a background job:
   $ para request wait --timeout 1h
   $ para proposal wait proposal-example --timeout 1h
   Each blocks with no token cost, then call `request_next` or `proposal_show`.

7. Optional: let para start the agent when a request can be claimed on this machine.
   THIS SPENDS TOKENS: every run starts a dun session, billed to whatever model
   account dun uses. Para starts nothing unless the file below exists on this
   machine. It is never in the vault and never synced. Write it with mode 600:

   $PARA_HOME/vaults/<vault>/agent.json
   {
     "command": ["dun", "-p", "Use the para tools: call request_next to claim a request, work only on that request, report with request_note, and finish with request_done or request_fail."],
     "max_concurrent": 1,
     "daily_limit": 10,
     "cwd": "/home/you/work"
   }

   command is an argument list, not a shell string. daily_limit counts starts per
   local day and survives a restart; max_concurrent is how many run at once. The
   environment of the command has PARA_REQUEST (the request id that woke it),
   PARA_HOME, and PARA_VAULT; nothing else from the vault is passed. Only the
   machine that is the vault's request runner starts anything.
   This example, dun -p with those words, is untested: it was not run against a
   real session. Try the command by hand first, with PARA_REQUEST set.
   $ para agent status
   $ para doctor

Para cannot stop an agent from using other tools. The rule is in the prompts: no
outward action without a proposal the owner approved in the chat. Para records the
owner's words with the decision, and what an agent reports is marked self-reported.
