Use para from dun.

1. Add one server per vault to `servers` in .dun/dun.local.json for this machine,
   or dun.json for the project:

{{config}}

2. Install the skill, so agents load the rules when they need them:
   $ para skill install
   Reinstall after upgrading para.

3. Check with /mcp.

4. Start with a prompt, as a slash command:
   /para-<vault>:orient      what para is, and how to work a vault
   /para-<vault>:bootstrap   an interview that fills a new vault
   /para-<vault>:review_cycle   how to file a proposal and act on the review
   /para-<vault>:process_meeting   turn a transcript into one proposal

5. Events record the actor `dun`. Change "--actor" to tell agents apart.

6. `para mcp` watches the vault for the session, with no polling. It sends a
   short message (notifications/message, logger "para") when a proposal you filed
   is decided, a request can be claimed by this install, or a request you
   claimed is cancelled. It holds ids and states only, never vault text, and
   names the tool to call next. The tools `proposal_wait` and `request_wait`
   block up to 60 seconds and return as soon as the state changes.
   dun adds the message to the conversation at the next tool result or turn. It
   does not start a turn on an idle session: this is read from dun's code, not
   run.
   Only a harness that cannot receive notifications needs a background job:
   $ para request wait --timeout 1h
   $ para proposal wait proposal-example --timeout 1h
   Each blocks with no token cost, then call `request_next` or `proposal_show`.

Para cannot stop an agent from using other tools. To enforce "no external action
without approval", use a dun hook or server-level limits. A hook can run para
proposal approved with the sha256 of the target, one NUL byte, and the draft; it
exits non-zero unless the owner approved that exact text.
