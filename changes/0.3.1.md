# 0.3.1

## People

- para keeps itself up to date. Once a day it checks the latest signed release (it sends nothing from your vaults; each check is logged as egress) and, at a quiet moment, installs it and restarts the service: no write for 15 minutes and no agent work in progress. A build from a checkout is never replaced; it only shows that a new version exists. Switches per machine in $PARA_HOME/install.properties: upgrade.check=false stops the check, upgrade.auto=false keeps the check but never installs. A vault blocks all update traffic with para vault config set egress.update deny. After an automatic install, the vault steps are filed as agent work, not run unattended; upgrade.vault_steps=auto runs the automated ones.
- para doctor says when the last check ran, whether a newer version exists, and whether auto-install is on. The web app shows a banner when a new version is available or was just installed.
- para serve now answers MCP over HTTP at /mcp, behind the same gate as the rest of the server. para setup --agent claude registers it with Claude Code (claude mcp add --transport http) using an agent key that only works from this machine, when the service runs; otherwise it uses stdio as before. After an upgrade, a connected Claude session picks up the new tools without a restart.
- para setup recovers after a failed claude mcp add: rerun it.

## Agents

- When para changes, the session instructions and a notice on your next call say so: call changes to see what changed. Over HTTP the server sends tools/list_changed after an upgrade; re-read the tool list.
- A stdio para mcp that runs a replaced binary says so on the next call: ask the owner to reconnect (/mcp) or to switch to the HTTP transport.
- Pending vault upgrade steps arrive as agent work titled "Vault upgrade: ...". "Vault upgrade: run the automated steps (dry run first)" means: ask the owner to run para vault upgrade --dry-run and then para vault upgrade.
