# 0.6.0

## People

- Two words change. A goal is a finite outcome with a done condition. This is what para called a project before. A project is now an ongoing thing with no end, such as a house, a product, or a company. An area stays the place for the rules and facts of one field.
- Every old project in your vault becomes a goal. Its tasks stay with it. Its id changes from `project-...` to `goal-...`. Every link to it is rewritten, and the old id still finds it. Receipts and events keep the old id and resolve it.
- A project has a state line: one line on where it stands. You edit it on the project page. Para records the day it last changed, and health warns when a line is missing or old.
- The web app has a Projects view at `/projects`. Each row shows the state line and its age, the goals in flight, what the project waits on, and its next cron. The project page at `/projects/<id>` shows the whole picture: goals with open tasks, what it waits on, the icebox, direct links, and history. Goal pages move to `/goals/<id>`. An old `/projects/<goal id>` link redirects.
- A goal that must wait is parked. A parked goal needs `resume_when`: the condition or the date that brings it back. Parked goals are the icebox of their project. Their open tasks leave Next until the goal is active again. A goal you had put off with no date (`someday`) becomes parked, and its reason becomes `resume_when`.
- A cron is work that repeats on a project. Each run makes an obligation for you, or a task under a goal of the project. While the goal of a cron is parked, its runs are skipped and it moves to its next date. Only the machine named in `request.runner` makes runs.
- A note, an Ask, an obligation, or a tracked document may link a project directly. A task reaches a project only through its goal. The one exception is a task a cron made.
- The command line has `para goal` (add, list, show, close, edit, link, signal, risk, rank, compare) and `para project` (add, show, retire). The goal flags named `--project` on task, note, question, and Ask commands still take a goal id.
- Upgrade. The vault format goes from 10 to 11. Do these steps in this order.
  1. Install 0.6.0 on every machine that opens the vault. A machine on 0.5 refuses a vault at format 11. There is no read-only mode. The step refuses to run while a machine seen in the last 14 days runs an older para. The message names the machine, its version, and when it was last seen. `--force` runs it anyway, and that machine then refuses the vault until you upgrade it.
  2. Run `para vault upgrade --dry-run`. It lists what step `goals` would do: goals re-prefixed, files moved, links rewritten, `someday` goals parked, parked goals with no `resume_when`. It changes nothing.
  3. Run `para vault upgrade`. It asks before it runs. `para upgrade --yes` runs the step too.
- The automatic install never runs step `goals`. It installs 0.6.0 and leaves the step pending. Only you run it, with one of the commands above. An agent cannot run it. An agent can only file the agent work that tells you to run it.
- Before step `goals` changes a file, it writes a snapshot of the whole vault to `$PARA_HOME/vaults/<id>/snapshots/<batch>.tar.gz`. The snapshot is on the machine that ran the step. It is never in the vault. If the snapshot cannot be written, the step stops and changes nothing. The run names the snapshot.
- Undo has limits. `para vault upgrade --undo <batch>` restores the files of that batch, and only on the machine that ran it. To go back further, restore the snapshot by hand: stop para on every machine, unpack the snapshot over the vault folder, start para. Anything written after the run is lost, including every write that used a `goal-...` id.
- After the step, an optional judgement step, `projects-sort`, is filed as agent work. For each area of kind project, and for each active goal with no done condition and no due date, an agent asks you one question: is it an ongoing project, a concept area, or a goal. The agent does not decide for you. You can dismiss one with health. This step does not hold the vault format back.
- A vault synced from an older machine can bring back an old `type: project` file after the step. Lint reports its id as taken (`former-id-taken`). Upgrade that machine, then run para again.

## Agents

- Old op names that meant a goal are refused. `op_run` and `ops_describe` answer "X removed in 0.6.0: use Y". Use Y.
- `project_add`, `project_show`, and `project_retire` are ops again, but for the new ongoing project. Given a goal id, they answer with the cause: "a goal since 0.6.0" and the goal op to use. `project_add` with `done_when` or `due` gives the same answer.
- Below format 11, `type: project` reads as a goal and the project ops refuse. Tell the owner to run `para vault upgrade`. Old files at format 10 are written back in the old form.
- Type words. `add`, `list`, `show`, and the `parent` of an `add` use `goal` for the finite type and `project` for the ongoing type. `add {type: goal, parent: <project id>}` sets the goal's project. `add {type: project}` takes title, `state_line`, and optionally area and owner. Close a project with `close {id, outcome: retired}` or `project_retire`.
- JSON keys. `project_name` is now `goal_name`. A `project` key that pointed at a goal is now `goal`. This covers task, question, obligation, agenda, today, and graph output and inputs. A `project` key now means an ongoing project. A reader outside para must change.
- Ids. A goal is `goal-<hash>`. A project is `project-<hash>`. A goal that had an id the owner chose keeps it. An old `project-<hash>` id of a goal still resolves through `former_ids` in the goal's frontmatter. A new id never reuses a former id. Do not read a type from an id prefix.
- Id changes. Any id change rewrites every link and keeps the old id in `former_ids`. Lint: `link-former` (a warning: the link still resolves) and `former-id-taken` (an error).
- On disk. Goals and their tasks are in `goals/`. Projects are in `projects/`. Goal status: active, paused, parked, done, dropped.
- Op renames. Only the last five rows are removed names; `project_add` and `project_show` keep their names for projects.

| Old op | New |
|---|---|
| project_add (made a goal) | goal_add, or add {type: goal} |
| project_show (a goal) | goal_show, or show {id} |
| project_edit | goal_edit, or edit {id, fields} |
| project_close | goal_close, or close {id, outcome} |
| project_list | list {type: goal} for goals, list {type: project} for projects |
| project_link_add | goal_link_add, or link {from, to, rel: link} |
| project_link_remove | goal_link_remove, or link {from, to, rel: link, remove: true} |

- The ops goal_signal, goal_rank, goal_compare, and goal_risk keep their names. The validation commands stay flat under `para goal`.
- New: `show` on a project returns one bundle under 8000 bytes: status, owner, state line and its age, goals in flight with their open tasks, what the project waits on, parked goals with `resume_when`, crons, direct links, and the last events of the project and its goals. A long list is cut and ends with "+N more" and the command to list the rest.
- Edit the state line with `edit {id, fields: {state_line}}`. Para sets `state_date` when the text changes. Do not write `state_date`.
- Park a goal with `edit {id, fields: {status: parked, resume_when}}`. `parked` without `resume_when` is refused. Setting the status back to active clears `resume_when`. Health warns on a parked goal with no `resume_when` (`goal_parked_no_resume_when`), an active project with no state line (`project_no_state_line`), and a state line older than the review cadence, or 14 days with no cadence (`project_state_stale`).
- `list` takes `status` with a `type`. `list {type: project}` lists active projects with a summary per row, stalest state first. `list {type: project, status: retired}` lists the rest. `list {type: goal, status: parked}` is the icebox. A status filter without `state` looks at open, later, and closed items.
- Links. `goal:` on a task, note, obligation, Ask, or tracked document names its goal. `project:` on a goal, note, obligation, Ask, or tracked document names a project. A task has no `project:`, except a task made by a cron, which carries `cron:` with it. At format 11, lint refuses `project:` on a task without `cron:`. Notes, Asks, obligations, and tracked documents may carry both.
- Crons. A cron is an obligation with `schedule: series`, `recur`, a `project`, and `makes`. `makes: obligation` (the default) makes an occurrence obligation with the project. `makes: task` with `goal` set makes a task under that goal. `makes: task` with no goal makes a task linked to the project, with `cron:` set. `owed_by` names who owes the work: `makes: task` needs a named agent (`agent:<name>`). `para tick` makes the runs on the `request.runner` machine only. Add one with `obligation_add {title, project, recur, makes, goal?, owed_by?}`. A cron whose goal is parked makes nothing and moves to its next date.
- Direct project links: `obligation_add {project}`, `add {type: note, parent: <project id>}`, and `add {type: ask, parent: <project id>}`. `doc_track` takes `project` for a tracked document.
- The open tasks of a parked goal leave Next, `needs_you`, and the order. The task files are not changed.
- Upgrade step `goals` is owner-only. An agent cannot run `vault_upgrade`. After the owner runs it, `projects-sort` appears as agent work with the instructions: ask the owner one question per item, then `doc_retype {id, type: project, fields: {status: active}}` and `edit` the goals to take the project as `project`, or `edit {id, fields: {kind: concept}}` for a concept area. A goal that needs an end gets `done_when`.
- An area has a kind (project or concept) and stays a facet. Do not make an area to track where a thing stands: make a project.
- GraphQL (the web app only): the old `Project*` operations are `Goal*`. The new type takes `Project*`.
