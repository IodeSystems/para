PARA, with an agent, and with IO

para is the PARA method — Projects, Areas, Resources, Archives — run with an agent that keeps it current, plus the part PARA leaves out: what comes in and what goes out. The point is one thing: act on the most impactful work you can, now.

Projects: short goals, full speed

A goal is a bounded outcome with a done-when. Its tasks form a graph with dependencies and blockers that carry reasons. The agent breaks it down, fills the gaps, and keeps it moving; you see what is stuck and why.

Areas: full understanding

Ongoing responsibilities — health, money, a client, a system you run — each with its policies, constraints, and exceptions inline, and a review date. Agents quote the source and cite the link, so you know what holds and why.

Resources: known, not copied

People and groups, how to reach them and who decides what. Your sources — mail, chat, tracker, wiki, calendar — and the documents you track. para links to where things live and keeps their versions; it does not make a second copy of your docs.

Archives: nothing lost

Closed work keeps its outcome and its history. Every agent write has a receipt with why, sources, and a diff, and most can be undone. Recent activity shows who changed what, across every machine.

Input: what came in, and what it changed

Your agent sweeps your sources. Each message becomes a task, a reply you owe, an answered question, or a digest line — and Input shows exactly what each one created, edited, or closed, for you to review.

Output: proposals before anything leaves

Every outward act — a reply, a PR, a ticket — is a proposal first, with why, impact, risk, and confidence. Batches, variations, revisions as you talk it through. You approve the exact text; para records what was sent.

Act on the most impactful thing

One rule decides what needs you. Next ranks it: what is due, what you owe someone, the quick replies, then the best impact for the effort, weighted by your goals' dates. One card at a time. Pinned keeps the plates you are juggling in view.

Talk to it like a teammate

Every item has a thread: change it, question it, redirect it. Capture with t from any page — a call, a promise made in a hallway — and the agent files it with the specification as you said it.

Your agent files. You direct.

para is MCP first. Agents write through MCP and get rendered text back. Claude Code, dun, or any MCP client works.

$ para setup --agent claude    # runs claude mcp add, installs the skill
$ para setup --agent dun
$ para setup --agent generic --agent-name scribe   # prints a name, URL, token once

Then open your agent, check /mcp, and run the bootstrap prompt for the first interview. An agent with only a shell can use para --actor NAME --why "reason" <command>. Setup for each harness: para help claude, para help dun.

Trust and privacy

These are invariants in the code, not preferences.

  • Plain files. A vault is a folder of markdown in Obsidian format. Git is optional. SQLite is a cache you can rebuild, never the source of truth.
  • One writer. All vault writes go through one package. A hand edit is detected and logged as an external edit. The event log is append-only and holds ids, metadata, and hashes, never content.
  • Nothing leaves without a log. Every path out is logged as an event. Anything outward waits for your approval.
  • Deny by default. The server checks, in order: client IP, Host, IP rule, token, scope, Origin. There is no --insecure. X-Forwarded-For is honored only from exact trusted proxies.
  • No OAuth, inbound or outbound.
  • Domains. A vault has a domain (such as life, iode, or corp). It opens only on a machine that lists that domain, so corp data stays on the corp machine. Only the owner changes a machine's domains, by CLI. No agent tool can.
  • No sync feature. Use any file-sync tool you like. A vault stays correct under it, because per-machine state lives outside the vault.
  • para fetches nothing. Your agent reads your mail, chat, and trackers with its own tools, and passes para a URL and text.

Install

Linux and macOS, amd64 and arm64.

$ curl -fsSL https://para.iodesystems.com/install.sh | sh
$ para setup

Installs the latest release to ~/.local/bin. Needs minisign: it checks the release signature, that the release is para's, and the tarball's sha256, and installs nothing if any check fails. Refuses to run as root. Read the script.

$ git clone https://github.com/IodeSystems/para.git && cd para
$ bin/doctor       # git, make, Go, node, pnpm, PATH
$ make install     # builds the UI and para into ~/.local/bin
$ para setup

Fix every FAIL line from bin/doctor first.

para setup asks about domains, the first vault, the service, sign-in, and an optional agent. A rerun skips what is done. para setup --dry-run prints every step and changes nothing. Then para serve for the web UI, on port 7700.

Releases are signed

Each release has a manifest with every tarball's sha256, signed with minisign. The key is shared with dun: key ID 2CC27A171DE03D42. Get the key from this site (minisign.pub) and compare the ID, then verify:

$ curl -fsSLO https://github.com/IodeSystems/para/releases/latest/download/para-manifest.json
$ curl -fsSLO https://github.com/IodeSystems/para/releases/latest/download/para-manifest.json.minisig
$ minisign -V -p minisign.pub -m para-manifest.json
